# Hmini_315 代码架构与 315 接收说明

本文档随 `Hmini_315` 仓库维护。

本文对应整理后的 Arduino Mega 2560 草图。当前阶段只实现并测试 315 MHz 接收器的数据接收、校验、解扰和通道解析；没有向 PX4 发送数据，也没有启用水桨、电机、舵机或断联保护。

## 1. 当前目录结构

```text
embedded/
├─ Hmini_315/
│  ├─ Hmini_315.ino          主程序入口、硬件对象和台架模式
│  ├─ RX315.ino              正式315接收与协议解析模块
│  ├─ WaterControl315.ino     保留的315水桨控制算法
│  ├─ YawCtrl.ino             跟踪微分器和水下姿态/深度PID
│  ├─ imu_data_decode.*       IMU数据内容解码
│  ├─ packet.*                IMU串口帧与CRC16解码
│  └─ MS5837.*                Bar30深度传感器驱动
├─ RX315_Diagnostics/
│  └─ RX315_Diagnostics.ino   独立的原始脉冲/UART抓包工具
└─ legacy/
   ├─ Hmini_315_before_cleanup.ino.txt
   ├─ HZ315_legacy.ino.txt
   └─ Radio_2.4G_and_315_original.ino.txt
```

Arduino IDE 会将 `Hmini_315` 目录中的所有 `.ino` 标签页合并编译，所以 `Hmini_315.ino` 可以直接调用 `RX315.ino` 中的函数。`legacy` 文件使用 `.txt` 后缀且位于草图目录外，不会参与编译。

## 2. 串口与当前运行模式

| 接口 | 用途 | 参数 | 当前是否启用 |
|---|---|---|---|
| `Serial` | USB串口监视器 | 115200 | 是 |
| `Serial1` | IMU | 115200 | 台架模式下否 |
| `Serial2` | 为后续Arduino→PX4保留 | 尚未配置 | 否 |
| `Serial3` / D15 / RX3 | 315接收器OUT | 9600、8N1 | 是 |

主草图只有一个模式开关：

```cpp
#define RX315_BENCH_TEST_ONLY 1
```

当前值为 `1`。因此：

- `setup()` 只执行 `Serial.begin()` 和 `rx315Begin()`；
- `loop()` 只执行 `rx315Update()`；
- SD、Bar30、IMU、ESC和舵机均不会初始化；
- `Serial2` 不会初始化，也不会向PX4发送数据。

完成通道确认和动力安全检查前，不应将该宏改为 `0`。

## 3. 已确认的315输入协议

315 MHz 是手柄到接收器的无线载波频率。接收器解调后，从OUT引脚输出9600 baud、8N1串口数据。

每帧固定24字节：

```text
00 | AD AD AD AD AD | FE | 10 | CRC | Data'[12] | BD DB BD
```

| 位置 | 长度 | 含义 |
|---|---:|---|
| `00` | 1 | 帧前导/分隔 |
| `AD×5` | 5 | 同步序列；解析器至少接受3个 |
| `FE` | 1 | 帧头标识 |
| `10` | 1 | 后续负载长度为16字节 |
| `CRC` | 1 | CRC-8，多项式`0x31` |
| `Data'[12]` | 12 | 加扰后的96位控制数据 |
| `BD DB BD` | 3 | 固定帧尾 |

CRC只覆盖线上加扰后的 `Data'[12]`。解扰掩码为：

```text
BD DB BD DB BD DB BD DB BD DB BD DB
```

逐字节执行：

```text
Data[i] = Data'[i] XOR mask[i]
```

解扰后的96位数据布局：

| 内容 | 位区间 | 位宽 |
|---|---:|---:|
| 通道0～3 | 0～43 | 每通道11位 |
| 通道4～9 | 44～79 | 每通道6位 |
| 帧序号 | 80～90 | 11位，0～2047循环 |
| 保留字段 | 91～95 | 5位 |

前4个通道映射为 `1000 + raw×1000/2047`，后6个通道映射为 `1000 + raw×1000/63`。

## 4. `Hmini_315.ino`

### 全局对象与变量

- `sensor`：MS5837/Bar30深度计。
- `dataFile`、`SDdata`、`FileName`：SD日志。
- `esc1～esc4`：前、后、左、右四个水桨ESC。
- `servo_left/right`：左右舵机。
- `Depth/Depth0/Temp`：相对深度、深度零点和温度。
- `roll_315/pitch_315/depth_d_315`：未来完成通道映射后使用的水桨控制输入；当前保持中立值。
- `phi/the/psi/d_att`：横滚、俯仰、航向和角速度。
- `errSum`：四路PID积分状态。

### `SDwrite()`

将累积的 `SDdata` 写入已打开文件，然后清空字符串。台架模式下不会执行。

### `writeNeutralOutputs()`

把四个ESC写为1490 us，并让左右舵机回到1000/2000 us。台架模式下舵机未绑定，因此该函数不会被调用。

### `setup()`

当前调用流程：

```text
Serial.begin(115200)
  -> rx315Begin()
  -> 因RX315_BENCH_TEST_ONLY=1而return
```

关闭台架模式后才会继续初始化IMU、SD、Bar30、ESC和舵机。

### `loop()`

当前调用流程：

```text
rx315Update()
  -> 因RX315_BENCH_TEST_ONLY=1而return
```

关闭台架模式后的保留流程会读取IMU和深度，并每50 ms根据 `rx315HasFreshFrame()` 选择水桨控制或中立输出。但当前还没有把 `rx315Channel()` 映射到 `roll_315/pitch_315`，所以不能直接恢复动力。

### `serialEvent1()`

完整模式下逐字节读取IMU的 `Serial1` 数据并交给 `packet_decode()`。当前台架模式没有初始化 `Serial1`。

## 5. `RX315.ino`

这是当前正式315接收模块，不再叫“diagnostic mode”。

### 对外接口

| 函数 | 作用 |
|---|---|
| `rx315Begin()` | 初始化 `Serial3@9600,8N1` 并打印启动信息 |
| `rx315Update()` | 清空接收缓冲区、逐字节解析，并每秒打印统计 |
| `rx315Channel(index)` | 返回指定通道映射后的1000～2000值；越界返回1500 |
| `rx315RawChannel(index)` | 返回指定通道原始11位/6位值；越界返回0 |
| `rx315HasFreshFrame()` | 已经收到有效帧且最近一帧不超过200 ms时返回true |
| `rx315LastFrameAgeMs()` | 返回最近有效帧年龄；尚无有效帧时返回`0xFFFFFFFF` |

这些接口只提供状态，不会执行断联保护或控制输出。

### 持久状态

`rx315_raw_channel[10]` 和 `rx315_pwm_channel[10]` 保存最近一个有效帧的通道，因此后续水桨映射和SBUS发送可以直接读取，不再依赖打印函数中的临时数组。

模块还保存：

- 总接收字节数；
- 有效帧数；
- CRC错误数；
- 帧尾错误数；
- 同步错误数；
- 根据11位序号估算的丢帧数；
- 最近有效帧时间；
- 当前序号和5位保留字段。

### `rx315Crc8()`

按初值0、多项式 `0x31` 计算CRC-8。调用时输入必须是加扰后的12字节线上数据。

### `rx315ExtractBits()`

从解扰后的12字节中按低位优先提取连续位字段，用于恢复10个通道、帧序号和保留位。

### `rx315Map11BitToPwm()` / `rx315Map6BitToPwm()`

分别把0～2047和0～63转换为1000～2000。

### `rx315DecodeData()`

执行：

```text
BD/DB解扰
  -> 提取ch[0]～ch[9]原始值
  -> 映射为1000～2000
  -> 提取帧序号和保留字段
  -> 统计序号跳变造成的丢帧
```

只有CRC和帧尾均正确时才会调用。

### `rx315HandlePayload()`

收满16字节负载后：

1. 检查固定帧尾 `BD DB BD`；
2. 对12字节 `Data'` 计算CRC；
3. 全部正确后调用 `rx315DecodeData()`；
4. 更新有效帧计数和最近有效时间；
5. 最多每100 ms打印一次通道。

坏帧只增加错误计数，不覆盖最近一次有效通道。

### `rx315ConsumeByte()`

逐字节状态机：

```text
等待00
  -> 等待至少3个AD及FE
  -> 等待长度10
  -> 收取16字节负载
  -> rx315HandlePayload()
  -> 回到等待00
```

遇到错误后调用 `rx315ResetParser()`，在下一帧重新同步。

### 串口输出

有效通道：

```text
RX315_VALID,frames=...,seq=...,ch=...,crc_errors=...,tail_errors=...,sync_errors=...
```

每秒状态：

```text
RX315_STATUS,bytes=...,valid=...,crc_errors=...,tail_errors=...,sync_errors=...,seq_lost=...,last_age_ms=...
```

## 6. `WaterControl315.ino` 与 `YawCtrl.ino`

`Marine_Remote_315()` 保留原来的水下控制算法：

- `roll_315/pitch_315` 控制左右水平推进；
- `depth_d_315` 与Bar30深度形成深度外环；
- IMU姿态和角速度参与横滚、俯仰、航向控制；
- `esc1/esc2` 控制深度和俯仰；
- `esc3/esc4` 控制前进和偏航；
- 运行数据写入SD。

当前尚未确认手柄物理操作与 `ch[0]～ch[9]` 的对应关系，因此没有给上述变量赋通道值。

`YawCtrl.ino` 保留 `TD()`、`fst()`、`sgn()` 和 `PID_outloop()`。旧2.4 GHz专用的 `PID_Remote()` 已移出正式控制链；同时修正了 `ki=0` 时积分限幅除零的问题。

## 7. 诊断工具

`RX315_Diagnostics.ino` 是独立草图，不参与 `Hmini_315` 编译。通过下面的宏选择：

```cpp
#define RX315_DIAGNOSTIC_MODE RX315_DIAGNOSTIC_RAW_CAPTURE
```

- `RX315_DIAGNOSTIC_RAW_CAPTURE`：使用D15/PCINT9采集最多160个电平脉宽，串口输入 `c` 启动。
- `RX315_DIAGNOSTIC_UART_PROBE`：使用 `Serial3@9600` 输出原始十六进制字节。

只有接收器协议再次发生变化或需要排查物理信号时才烧录该草图。

## 8. 已归档的旧代码

- `Hmini_315_before_cleanup.ino.txt`：整理前完整主草图快照。
- `HZ315_legacy.ino.txt`：旧4800 baud、`AA×5 + FE F1`协议；与当前接收器不兼容。
- `Radio_2.4G_and_315_original.ino.txt`：原2.4 GHz和315水桨控制函数快照。

正式草图不再创建 `bfs::SbusRx`、不再使用 `IsRadioReceive`，也不再初始化 `Serial2`。这为后续Arduino→PX4输出保留了接口。

## 9. 当前调用流程

```text
315接收器OUT
  -> Mega D15 / Serial3@9600
  -> rx315Update()
  -> rx315ConsumeByte()
  -> 帧头与长度同步
  -> rx315HandlePayload()
       ├─ 帧尾检查
       └─ CRC-8检查
  -> rx315DecodeData()
       ├─ BD/DB解扰
       ├─ 保存raw[10]
       ├─ 保存pwm[10]
       └─ 保存序号/统计
  -> USB串口显示
```

当前流程到此结束，不进入水桨控制，也不进入PX4。

## 10. 下一阶段边界

下一阶段应先完成每个手柄操作对应通道的实测，再决定：

- 哪些通道写入 `roll_315/pitch_315/depth_d_315`；
- 哪些通道送给PX4；
- 通道反向、中位死区和开关阈值；
- 断联后的安全值和SBUS failsafe位。

由于现有接线进入PX4的PPM/SBUS RC IN，后续需要输出标准SBUS，而不能把当前24字节9600 UART帧原样送入该接口。Mega2560上的现有SBUS库使用非反相UART并要求外部反相电路，实施前必须确认现有“SBUS口”的电气结构。
